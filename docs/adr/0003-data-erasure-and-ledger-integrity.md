# ADR 0003: 삭제 요청 시 원장 무결성과 개인정보 제거의 양립

- 상태: 수락됨
- 날짜: 2026-08-28
- 관련 이슈: #21
- 관련 불변 규칙: INV-012(정정은 과거를 파괴하지 않는다), INV-030(중요 상태 변화는 append-only 감사 사건), INV-031(민감정보 기본 미수집), INV-035(과거 상태 재구성)

## 문제

개인정보 삭제 요청(예: GDPR 파기 요구)이 들어오면, append-only 원장과 "과거 상태 재구성"은 원문 이벤트를 유지해야 하고, 개인정보 제거 의무는 해당 이벤트에서 개인정보를 없애야 한다. 두 요구는 표면적으로 충돌한다.

## 결정

1. **원장 이벤트는 절대 수정/삭제하지 않는다.** 무결성 검증(`verifyLedgerIntegrity`)은 버전 연속성과 이벤트 id 유일성에 기반하므로, 과거 이벤트를 고쳐 쓰면 원장 전체의 신뢰가 깨진다.
2. **개인정보는 원장에 저장하지 않는 것이 기본값이다(INV-031).** credential은 해시만 저장하고, 관찰 detail은 레닥션 후 해시로 대체하며(#17), 컨텍스트 statement에 PII를 쓰지 않는다. 삭제 요청의 대상이 되는 원문 데이터는 원장에 존재하지 않는다.
3. **원문이 필요한 필드는 subject별 암호화 키(crypto-shredding)로 분리한다.** 부득이하게 개인 데이터를 담아야 하는 필드는 subject(사용자)별 데이터 키로 암호화해 저장하고, 삭제 요청 시 **해당 subject의 키를 폐기**한다. 원장 이벤트는 유지되지만 키 없이는 복호화할 수 없어 개인정보 제거 의무를 만족한다.
4. **삭제 처리는 톰스톤 이벤트로 기록한다.** `DataErasureRequested`/`DataErasureApplied` 이벤트를 원장에 append해 누가·언제·어떤 subject에 대해 처리했는지 감사 사슬로 남긴다. 읽기 모델(read tables)에서는 해당 subject의 행을 삭제/익명화한다.
5. **법적 보존(hold)은 삭제를 보류한다.** `isWithinRetention`의 legalHold가 활성인 동안 삭제 처리를 보류하고, hold 해제 후 처리한다.

## 검토한 대안

- **과거 이벤트를 수정/삭제한다**: 원장 무결성(INV-035)과 감사 사슬이 파괴되므로 기각. 제품 목적 자체가 부정.
- **원장 전체를 재작성해 개인정보를 걷어낸다**: 동일하게 무결성 검증이 무의미해지고 모든 파생 분석의 역추적이 깨지므로 기각.
- **개인정보를 원장에 저장하지 않는 것만으로 충분하다고 본다**: 기본 전략으로 채택하되, 원문이 필요한 정당한 필드까지 금지하면 제품 기능이 제한되므로 crypto-shredding을 보완으로 채택.

## 결과

- 원장은 append-only와 무결성 검증을 유지하면서, 키 폐기 + 톰스톤 이벤트 + 읽기 모델 정리로 삭제 의무를 만족한다.
- 구현 상태: `security.ts`의 `isWithinRetention`(legal hold)과 `verifyLedgerIntegrity`(복원 검증)가 이 ADR의 검증 가능한 기반이다. crypto-shredding 키 관리와 `DataErasureApplied` 이벤트 도입은 후속 이슈로 진행한다.
